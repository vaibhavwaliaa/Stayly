HOW TO USE THIS FILE
------------------------------------------------------------------------------

1. Work top to bottom, phase by phase. Do not skip phases — each one assumes
   the previous phases already exist in your repo.

2. Two kinds of lines in this file:

     [YOU DO]       -> a manual action outside the AI (install something,
                        run a terminal command, click a button on a website).

     [PASTE TO AI]  -> literal text you copy and paste into your AI tool,
                        exactly as written. Where you see <ANGLE BRACKETS>,
                        replace with your own value (name, URL, etc).

3. Best tool to use: an AGENTIC coding assistant that can read and write
   files directly in your project folder — Claude Code (terminal, VS Code,
   or JetBrains), or Cursor. These prompts are written for that workflow:
   the AI creates/edits real files, runs commands, and you just review.

   If you're instead using a plain chat window with no file access
   (ChatGPT web, claude.ai without Code Execution), you'll need to manually
   copy each code block the AI gives you into the right file path — the AI
   will tell you the path in its response.

4. After every prompt, run the line marked "VERIFY:" before moving to the
   next prompt. Catching a broken step immediately is 10x faster than
   debugging three phases later when five things are broken at once.

5. If a step breaks and you don't immediately know why, do NOT keep
   re-prompting randomly. Use the DEBUG PROMPT TEMPLATE at the very end of
   this file — it's written to get you a precise diagnosis instead of the
   AI guessing.

6. A note on "exactly like Airbnb": copy the LAYOUT and UX PATTERNS — the
   grid of listing cards, the sticky pill-shaped search bar, the split
   gallery/booking-panel listing page, the calendar-based date picker. None
   of that is Airbnb's intellectual property, it's just good, well-known UX.
   Do NOT use Airbnb's actual logo, wordmark, or copyrighted photography —
   pick your own project name (e.g. "Stayly", "Roamly", "Nestly") and use
   placeholder/stock imagery (Section 6 covers exactly how). This is also
   literally what the assignment brief asks for: "closely resemble the
   Airbnb experience" — not "use Airbnb's actual branding."

7. Total estimated time if you follow this file start to finish: 26-30
   hours of focused work. Don't rush Phase 2 (database schema) — a shaky
   schema causes rework in every phase after it.

PHASE 7 — BOOKINGS API (the core booking flow + overlap validation)
================================================================================

[PASTE TO AI]
--------------------------------------------------------------------
In services/availability.py, add a function:

    def has_overlap(db, listing_id, check_in, check_out,
                     exclude_booking_id=None) -> bool

It should return True if any CONFIRMED booking on that listing has
check_in < the new check_out AND check_out > the new check_in (a half-open
interval overlap check — this correctly allows back-to-back bookings where
one checkout date equals another's check-in date). Support
exclude_booking_id so the same check can be reused for "editing" a
booking's dates later without it colliding with itself.

Now create backend/app/routers/bookings.py with prefix "/bookings" (mount
under a router that also needs the auth dependency you'll build in Phase
9 — for now, accept a guest_id query param or header as a temporary stand-
in and note clearly with a TODO comment that Phase 9 will replace it with
a real authenticated user dependency):

POST /bookings
  Body: listing_id, check_in, check_out, guests_count.
  Validate: check_out > check_in (400 if not), guests_count <= the
  listing's max_guests (400 if not), listing exists and is_active (404 if
  not). Call has_overlap — if True, raise HTTPException(409, "Selected
  dates are no longer available"). Otherwise compute nightly_rate_snapshot
  = listing.price_per_night, nights = (check_out - check_in).days,
  total_price = nightly_rate_snapshot * nights (for now, no extra fees at
  the API level — fees are a frontend-only display concern in the price
  breakdown, described in Phase 12). Create and return the booking.

GET /bookings/me
  Return the current guest's bookings, newest first, each with a nested
  lightweight listing summary (id, title, city, cover photo). Split is NOT
  done server-side — return everything and let the frontend group into
  upcoming/past by comparing dates to today.

GET /listings/{id}/bookings
  Owner-only (listing.host_id must match the current user — again, stub
  the auth check with a clear TODO for Phase 9). Returns all bookings for
  that listing.

PATCH /bookings/{id}/cancel
  Only the guest who made the booking (or the host who owns the listing)
  can cancel. Sets status to "cancelled". 404 if not found, 403 if not
  authorized.

Show me the full bookings.py.
